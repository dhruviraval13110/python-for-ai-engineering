# Contributing

Thank you for your interest in contributing to this project.

## Ways to Contribute

You can contribute by:

- Reporting bugs
- Suggesting new features
- Improving documentation
- Optimizing existing code
- Adding new Python examples
- Improving code quality
- Writing tests

---

## Development Setup

Clone the repository:

```bash
git clone https://github.com/dhruviraval13110/python-for-ai-engineering.git
```

Navigate into the project:

```bash
cd python-for-ai-engineering
```

Create a virtual environment:

```bash
python -m venv .venv
```

Activate it.

Windows

```bash
.venv\Scripts\activate
```

Linux/macOS

```bash
source .venv/bin/activate
```

Install dependencies:

```bash
pip install -r requirements.txt
```

---

## Coding Standards

Please follow:

- PEP 8
- Meaningful variable names
- Modular design
- Clear comments when necessary
- Keep functions small and reusable

---

## Commit Message Style

Examples:

```
feat: add expense tracker example

fix: resolve division by zero bug

docs: improve README

refactor: simplify utility functions

test: add unit tests
```

---

## Pull Requests

Before submitting:

- Ensure code runs correctly
- Update documentation if needed
- Keep pull requests focused
- Follow the repository structure

Thank you for helping improve this project.

10. Which step is most expensive?
11. What would you log?
12. What would you test?
13. What would you monitor in production?
14. Which assumption is most dangerous?
15. What alternative design would you reject and why?

Create a small module with one public function. Give it a precise type signature. Validate inputs at the boundary. Keep transformation logic separate from I/O. Return a predictable result. Write a happy-path test, a boundary test, and an invalid-input test.

### Review drill

Read your implementation as if you were reviewing someone else’s pull request. Look for unclear names, hidden state, duplicated logic, surprising defaults, broad exception handling, missing tests, and documentation that describes what the code does but not why.

### Interview follow-up

An interviewer may start with “Explain Contributing” and then immediately ask for an example, a limitation, a complexity discussion, a failure case, and a production design. Practice answering in that order instead of giving a memorized definition.
